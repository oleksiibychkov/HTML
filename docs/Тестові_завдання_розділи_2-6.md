### Рівень 1 — Знання

**Тест 2.1.** Як оголосити мутабельну змінну в Rust?

- A) `var mut x = 5;`
- B) `let mut x = 5;`
- C) `mut let x = 5;`
- D) `let x: mut i32 = 5;`

<details><summary>Відповідь</summary>

**B)** `let mut x = 5;`

Ключове слово `mut` ставиться між `let` та іменем змінної. Це свідоме рішення дизайну Rust — ви повинні **явно** вказати, що змінна буде змінюватись.

</details>

**Тест 2.2.** Який діапазон значень має тип `u8`?

- A) від –128 до 127
- B) від 0 до 255
- C) від 0 до 65 535
- D) від –256 до 255

<details><summary>Відповідь</summary>

**B)** від 0 до 255

`u8` — беззнаковий 8-бітний цілий тип. Префікс `u` означає *unsigned* (без знака), а `8` — кількість біт. Формула: від 0 до 2⁸ – 1 = 255.

</details>

**Тест 2.5.** Чим shadowing (`let x = x + 1;`) відрізняється від мутабельності (`x = x + 1;`)?

- A) Shadowing дозволяє змінити тип змінної, мутабельність — ні
- B) Мутабельність дозволяє змінити тип змінної, shadowing — ні
- C) Різниці немає — це два синтаксиси для одного й того самого
- D) Shadowing працює лише з числовими типами

<details><summary>Відповідь</summary>

**A)** Shadowing дозволяє змінити тип змінної, мутабельність — ні

При shadowing (`let x = ...` повторно) створюється **нова** змінна, тому тип може бути іншим. Наприклад, `let x = "hello"; let x = x.len();` — спочатку `&str`, потім `usize`. З `mut` можна змінювати лише значення в межах одного типу.

</details>

**Тест 2.6.** Що виведе цей код?

```rust
fn main() {
    let x = 5;
    let x = x + 1;
    let x = x * 2;
    println!("{}", x);
}
```

- A) `5`
- B) `6`
- C) `12`
- D) Помилка компіляції: подвійне оголошення змінної `x`

<details><summary>Відповідь</summary>

**C)** `12`

Це **shadowing**: кожне `let x = ...` створює нову змінну з тим самим ім'ям. Перша `x = 5`, друга `x = 5 + 1 = 6`, третя `x = 6 * 2 = 12`. Помилки компіляції немає — shadowing дозволений у Rust.

</details>

**Тест 2.8.** Що станеться при виконанні цього коду в debug-режимі?

```rust
fn main() {
    let x: u8 = 255;
```

- A) Виведе `0` (значення обернеться)

</details>

### Рівень 1 — Знання

**Тест 3.1.** Який правильний синтаксис оголошення функції з параметром та поверненням значення?

- A) `function calculate(x: i32) -> i32 { x * 2 }`
- B) `fn calculate(x: i32) -> i32 { x * 2 }`
- C) `fn calculate(x) -> i32 { x * 2 }`
- D) `def calculate(x: i32) -> i32 { x * 2 }`

<details><summary>Відповідь</summary>

**B)** `fn calculate(x: i32) -> i32 { x * 2 }`

Функції в Rust оголошуються ключовим словом `fn`. Тип кожного параметра обов'язково вказується після двокрапки. Тип повернення вказується після стрілки `->`.

</details>

---

**Тест 3.2.** Чим відрізняється statement від expression у Rust?

- A) Statement повертає значення, expression — ні
- B) Expression повертає значення, statement — ні
- C) Різниці немає — це синоніми
- D) Statement використовується лише у функціях, expression — лише у циклах

<details><summary>Відповідь</summary>

**B)** Expression повертає значення, statement — ні

Expression (вираз) обчислюється і повертає значення: `5 + 3`, `if x > 0 { 1 } else { -1 }`. Statement (інструкція) виконує дію без повернення значення: `let x = 5;`, `println!("hello");`. Ключова відмінність: **блок `{ }` — це expression**, і його значення — це останній вираз без крапки з комою.

</details>

---

**Тест 3.3.** Що повернеться з цієї функції?

```rust
fn get_status(battery: u8) -> &str {
    if battery > 50 {
        "OK"
    } else {
        "Low"
    }
}
```

- A) Помилка: `if` не може повертати значення
- B) `"OK"` якщо battery > 50, інакше `"Low"`
- C) Завжди `"Low"`, бо `"OK"` не має `return`
- D) Помилка: функція не має оператора `return`

<details><summary>Відповідь</summary>

**B)** `"OK"` якщо battery > 50, інакше `"Low"`

У Rust `if` — це expression, що повертає значення. Останній вираз у функції (без крапки з комою) автоматично повертається — `return` не потрібен. Обидві гілки `if/else` повертають `&str`, що відповідає типу повернення функції.

</details>

**Тест 3.4.** Що станеться при компіляції цього коду?

```rust
fn add(a: i32, b: i32) -> i32 {
    a + b;
}
```

- A) Код скомпілюється нормально
- B) Помилка: функція нічого не повертає, хоча очікується `i32`

**Тест 3.5.** Яка різниця між цими двома фрагментами?

```rust
// Фрагмент A
fn double(x: i32) -> i32 {
    x * 2
}

// Фрагмент B
fn double(x: i32) -> i32 {
```

- A) Фрагмент A — помилка, потрібен `return`
- B) Фрагмент B — помилка, `return` заборонений у Rust

**Тест 4.1.** Який цикл у Rust є нескінченним і виходить лише через `break`?

- A) `while true { }`
- B) `for { }`
- C) `loop { }`
- D) `repeat { }`

<details><summary>Відповідь</summary>

**C)** `loop { }`

`loop` — спеціальна конструкція для нескінченних циклів. На відміну від `while true`, компілятор знає, що цикл нескінченний, що дозволяє кращу оптимізацію та type inference. Наприклад, `loop` може повертати значення через `break`.

</details>

**Тест 4.2.** Який діапазон створює послідовність 1, 2, 3, 4, 5?

- A) `1..5`
- B) `1..=5`
- C) `1...5`
- D) `1->5`

<details><summary>Відповідь</summary>

**B)** `1..=5`

`1..=5` — це **включний** діапазон (inclusive range), що містить і 1, і 5. А `1..5` — це **виключний** діапазон, що містить 1, 2, 3, 4, але **не** 5. Синтаксис `1...5` і `1->5` не існують у Rust.

</details>

**Тест 4.3.** Що вимагає `match` у Rust на відміну від `switch` у C/Java?

- A) Мати гілку `default`
- B) Покривати всі можливі значення (exhaustive matching)
- C) Працювати лише з цілими числами
- D) Мати щонайменше 3 гілки

**B)** Покривати всі можливі значення (exhaustive matching)

<details><summary>Відповідь</summary>

**C)** `Внутрішня: 20`, `Зовнішня: 10`

У внутрішньому блоці `let x = 20` створює **нову** змінну `x`, що **затінює** (shadows) зовнішню. Всередині блоку видно лише внутрішню `x = 20`. Після виходу з блоку внутрішня `x` знищується, і знову стає видимою зовнішня `x = 10`, яка ніколи не змінювалась.

</details>

**Тест 6.6.** Яка різниця між затіненням (shadowing) в області видимості та зміною мутабельної змінної?

```rust
// Варіант A: Shadowing
let x = 10;
{
    let x = 20;  // нова змінна
}
// x = 10

// Варіант B: Мутабельність
let mut x = 10;
{
    x = 20;  // змінюємо існуючу
}
// x = 20
```

- A) Різниці немає
- B) У варіанті A зовнішня `x` не змінилась (залишилась 10), у варіанті B — змінилась (стала 20)
- C) Варіант A не скомпілюється
- D) Варіант B не скомпілюється

<details><summary>Відповідь</summary>

**B)** У варіанті A зовнішня `x` не змінилась (залишилась 10), у варіанті B — змінилась (стала 20)

Shadowing створює **нову** змінну з тим самим ім'ям — оригінал залишається незмінним. Мутабельне присвоювання змінює **існуючу** змінну. Після виходу з внутрішнього блоку: у варіанті A `x = 10` (оригінал), у варіанті B `x = 20` (було змінено).

</details>

### Рівень 3 — Застосування

**Тест 6.7.** Навіщо використовувати штучну область видимості (explicit block)?

```rust
fn process_data() {
    let result;
    {
        let large_buffer = vec![0u8; 10_000_000]; // 10 МБ
        result = analyze(&large_buffer);
    } // large_buffer звільняється тут
    
    // Подальша робота з result, але без 10 МБ в пам'яті
    println!("Результат: {}", result);
}
```

- A) Це лише стилістичний прийом для читабельності
- B) Щоб звільнити ресурси **раніше**, ніж в кінці функції
- C) Rust вимагає штучні блоки для великих структур
- D) Штучні блоки прискорюють компіляцію

<details><summary>Відповідь</summary>

**B)** Щоб звільнити ресурси **раніше**, ніж в кінці функції

Штучний блок `{ }` обмежує область видимості `large_buffer`. Після закриваючої `}` 10 МБ пам'яті звільняються негайно, а функція продовжує роботу з `result`. Без блоку `large_buffer` залишався б у пам'яті до кінця функції.

</details>

**Тест 6.8.** Що виведе цей код?

```rust
fn main() {
    let mut x = 1;
    
    for i in 0..3 {
        let y = i * 10;
        x += y;
    }
    
    println!("x = {}", x);
    // println!("y = {}", y);  // Розкоментувати?
}
```

- A) `x = 31`, а розкоментований рядок виведе `y = 20`
- B) `x = 31`, а розкоментований рядок спричинить помилку компіляції
- C) `x = 30`, а розкоментований рядок виведе `y = 20`
- D) Помилка компіляції вже в закоментованому вигляді

<details><summary>Відповідь</summary>

**B)** `x = 31`, а розкоментований рядок спричинить помилку компіляції

Цикл: ітерація 0 → `y=0`, `x=1+0=1`; ітерація 1 → `y=10`, `x=1+10=11`; ітерація 2 → `y=20`, `x=11+20=31`. Змінна `y` оголошена всередині циклу, тому після циклу вона не існує. Спроба використати `y` поза циклом — помилка `cannot find value 'y' in this scope`.

</details>

**Тест 6.9.** Чому область видимості є критично важливою для Rust, на відміну від мов зі збирачем сміття?

- A) Область видимості визначає порядок виконання інструкцій
- B) Rust використовує область видимості як основний механізм керування пам'яттю — вихід із scope = автоматичне звільнення ресурсів, без потреби у збирачі сміття
- C) Область видимості потрібна лише для читабельності коду
- D) У Rust є збирач сміття, а область видимості — лише додатковий механізм

<details><summary>Відповідь</summary>

**B)** Rust використовує область видимості як основний механізм керування пам'яттю — вихід із scope = автоматичне звільнення ресурсів, без потреби у збирачі сміття

В Rust **немає** збирача сміття. Область видимості безпосередньо пов'язана з системою **ownership**: коли змінна-власник виходить із scope, ресурси звільняються детерміновано. Це дає передбачувану продуктивність і гарантує відсутність витоків пам'яті на рівні компілятора.

</details>

**Тест 6.10.** Розгляньте код. Скільки разів буде створено та знищено змінну `buffer`?

```rust
fn main() {
    for i in 0..5 {
        let buffer = [0u8; 1024];
        println!("Ітерація {}: {:?}", i, &buffer[..3]);
    }
}
```

- A) 1 раз створено, 1 раз знищено (після циклу)
- B) 5 разів створено, 5 разів знищено (кожну ітерацію)
- C) 5 разів створено, 1 раз знищено (після циклу)
- D) 1 раз створено, 5 разів знищено

<details><summary>Відповідь</summary>

**B)** 5 разів створено, 5 разів знищено (кожну ітерацію)

Тіло циклу `for` — це окрема область видимості, що створюється на **кожній ітерації**. Змінна `buffer` оголошується заново кожен раз і знищується при закритті `}` тіла циклу. За 5 ітерацій: 5 створень + 5 знищень.

</details>
